# 二十、不要使用 LocalStorage 作为最终方案

特别注意：

**不能使用 localStorage 作为多人共享数据库。**

例如：


只能用于本地缓存/临时状态，不能作为本项目宾客名单的最终数据源。

因为：

```text
A电脑 localStorage

B电脑 localStorage
```

无法实现真正的多人共享。

# 十四、物料表格宽度

表格宽度不要写死。

```text

│ 表格────────────────────────────────────── │
└────────────────────────────────────────────┘
```

iPad：

```text
┌───────────────────────────────┐
│             衣物              │
│ 表格───────────────────────── │
└───────────────────────────────┘
```

所有列应该根据可用空间合理调整。

尤其“物品名称”和“备注”应该拥有足够宽度。

可以使用：

```css
table-layout: fixed;
```

结合：

```css
width: 100%;
```

以及合理的列宽比例。

把：

```text
## 第一环节
```

渲染成：

**二级标题。**

---

# 三十四、主持词编辑器形式

请根据用户体验选择合理实现方式。

我希望最终达到：

> “编辑 Markdown，同时能够看到 Markdown 渲染后的效果。”

可以采用：

### 方案 A

左边：

```text
Markdown 编辑区
```

右边：

```text
实时预览
```

例如：

```text
┌──────────────────────┬──────────────────────┐
│ # 开场               │ 开场                 │
│                      │                      │
│ 大家好……             │ 大家好……             │
│                      │                      │
│ ## 第一环节          │ 第一环节              │
│                      │                      │
└──────────────────────┴──────────────────────┘
```

如果采用这种方案，请保证在电脑和 iPad 横屏下都能良好显示。

---

也可以采用：

### 方案 B

一个编辑区域 + 编辑模式/预览模式切换。

但是：

**无论采用哪种方案，都必须能够实时看到 Markdown 渲染效果。**

如果你认为左右分栏更适合本项目，请优先采用左右分栏。

---

# 三十五、主持词不要使用普通 textarea 作为最终显示

不要只是：

```html
<textarea>
```

然后用户看到纯 Markdown 字符。

需要有：

> Markdown → HTML

的实时渲染。

可以使用成熟的 Markdown parser，例如：

* markdown-it
* marked

优先选择安全、成熟、维护正常的库。

---

# 三十六、Markdown 安全

这是一个重要要求。

因为 Markdown 最终会渲染成 HTML。

请避免用户输入恶意 HTML/JavaScript 导致 XSS。

如果 Markdown parser 允许原始 HTML：

请进行合理的 HTML sanitize。

例如可以使用：

* DOMPurify

或者关闭危险的 HTML 渲染能力。

最终要求：

> 主持词可以正常使用 Markdown，但不能通过主持词内容执行任意 JavaScript。

---

# 三十七、主持词自动保存

主持词不是点击“提交”之后才保存。

希望：

> 用户修改后自动保存。

可以采用合理的 debounce，例如：

```text
用户停止输入 500~1000 ms
↓
自动保存
↓
数据库
```

不要每输入一个字符就发送一次数据库请求。

# 三十八、主持词同步

主持词与其他模块一样：

**所有打开网页的人共享同一份主持词。**

B 页面自动出现：

```text

各位亲朋好友，大家好！
```

如果 B 修改：

```text

```

A 也能够看到更新。

# 三十九、主持词并发编辑

多人可能同时编辑主持词。

这个阶段不要求实现类似 Google Docs 那种字符级实时协作。

但是需要：

1. 数据保存到云端；
2. 数据能够同步；
3. 页面刷新后内容不会丢失；
4. 不要因为普通的页面刷新而恢复旧内容。

如果当前使用的后端支持实时监听，可以直接利用。

如果存在多人同时编辑导致覆盖的问题，请在代码中尽可能采用合理的：

* updated_at；
* revision；
* 乐观更新；

等机制。

并在 README 中说明当前协作模型。
